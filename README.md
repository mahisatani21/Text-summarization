## Overview

The service exposes a REST API that accepts raw text and returns an abstractive summary generated by a fine-tuned/benchmarked transformer model (e.g. `sshleifer/distilbart-cnn-6-6`, `t5-small`, `google/flan-t5-small`). Every request is instrumented for latency, throughput, and resource usage, and every training/tuning run is logged to MLflow for reproducibility and comparison.

The project is organized around four pillars:

| Pillar | Tool | Purpose |
|---|---|---|
| **Modeling** | Hugging Face `transformers` | Candidate model benchmarking and generation |
| **Optimization** | Optuna | Automated search over generation hyperparameters (`num_beams`, `length_penalty`, etc.) |
| **Tracking & Registry** | MLflow | Experiment logging, run comparison, and model registry (`TextSummarizerBest`) |
| **Orchestration** | ZenML | Reproducible, step-based ML pipelines (`.zen`) |
| **Serving & Ops** | FastAPI, Prometheus, Grafana | Inference API, metrics scraping, and live dashboards |

---

## Key Features

- 🤖 **Multi-model benchmarking** — Compare BART, DistilBART, and T5-family models on latency, memory footprint, and ROUGE score.
- 🎯 **Automated hyperparameter tuning** — Optuna-driven search over generation parameters, optimized for ROUGE-L.
- 📊 **Full experiment tracking** — Every run (params, metrics, artifacts, system resource usage) logged to MLflow.
- 🗂️ **Model registry** — Best-performing model versioned and served from the MLflow Model Registry.
- 🔁 **Pipeline orchestration** — ZenML steps for repeatable train/tune/evaluate workflows.
- 🚀 **Production-ready API** — FastAPI service with request validation via Pydantic.
- 📈 **Real-time observability** — Prometheus metrics (request rate, latency histograms, token length) and Grafana dashboards with alerting.
- ✅ **Quality gates in CI/CD** — ROUGE regression tests ensure model changes don't silently degrade summary quality.
- 🐳 **One-command deployment** — Full stack (API, MLflow, Prometheus, Grafana) via Docker Compose.
- 🖥️ **System resource profiling** — CPU and memory (RSS) tracked per run via `psutil` for deployment sizing decisions.

## Getting Started

### Prerequisites

- Python 3.10+
- Docker & Docker Compose (for the full production stack)
- ~2 GB free RAM (for local CPU-based model inference)

### Installation

```bash
# Clone the repository
git clone https://github.com/mahisatani21/Text-summarization.git
cd Text-summarization

# Create and activate a virtual environment
python -m venv venv
venv\Scripts\activate        # Windows
source venv/bin/activate     # macOS/Linux

# Install PyTorch (CPU build) first to save bandwidth, then the rest
pip install torch --index-url https://download.pytorch.org/whl/cpu
pip install -r requirements.txt
```

### Running Benchmarks & Tuning

```bash
# Benchmark candidate Hugging Face models (logs to MLflow)
python src/train.py

# Run Optuna hyperparameter tuning over generation parameters
python src/tune.py
```

MLflow runs are saved locally under `./mlruns` unless a tracking server is configured.

### Launching the Production Stack

Spin up the FastAPI service alongside MLflow, Prometheus, and Grafana:

```bash
cd docker
docker compose up --build -d
```

| Service | URL | Credentials |
|---|---|---|
| FastAPI Service | http://localhost:8000 | — |
| MLflow Tracking Server | http://localhost:5000 | — |
| Prometheus UI | http://localhost:9090 | — |
| Grafana Dashboard | http://localhost:3000 | `admin` / `admin` |

See [`EXECUTION_GUIDE.md`](./EXECUTION_GUIDE.md) for a full step-by-step walkthrough.

## Using the API

Once the FastAPI service is running, interactive API docs are available at `http://localhost:8000/docs` (Swagger UI).

**Example request:**

```bash
curl -X POST "http://localhost:8000/summarize" \
  -H "Content-Type: application/json" \
  -d '{
        "text": "Long article text goes here...",
        "max_length": 130,
        "min_length": 30
      }'
```

**Example response:**

```json
{
  "summary": "Concise generated summary of the input text.",
  "model": "sshleifer/distilbart-cnn-6-6",
  "latency_seconds": 0.87
}
```

> ⚠️ Exact request/response schema is defined by the Pydantic models in `src/` — confirm field names against the running `/docs` endpoint if they differ.

Prometheus metrics for the service are exposed at `http://localhost:8000/metrics`.

## Experiment Tracking with MLflow

Navigate to `http://localhost:5000` and select the **`Text_Summarization_System`** experiment.

**Compare runs:** Select multiple runs (model benchmarks or Optuna trials) and click **Compare** to see side-by-side parameters (`model_name`, `num_beams`, `length_penalty`) and metrics (`rougeL`, `avg_latency_sec`, `system_cpu_utilization_percent`, `system_memory_usage_mb`).

**Filter runs** using SQL-like queries in the search bar:

```sql
metrics.rougeL > 0.15
params.model_name = 'sshleifer/distilbart-cnn-6-6'
params.num_beams >= 4 and metrics.avg_latency_sec < 2.0
```

**Visualize hyperparameter effects:** Use the **Parallel Coordinates Plot** (map `num_beams`, `length_penalty` → `rougeL`) or a **Scatter Plot** (`length_penalty` vs. `rougeL`) under a run comparison's Visualizations tab.

**Inspect the registered model:** Under the **Models** tab, open **`TextSummarizerBest`** to view its source run, input/output schema, and saved artifacts (tokenizer, model weights, generation config).

**Export run history to CSV:**

```bash
python mlflow_export.py
```

This produces `mlflow_runs.csv` for offline analysis in Excel/Pandas.

**System resource tracking:** Every run logs `system_cpu_utilization_percent`, `system_memory_usage_mb` (peak RSS), and `system_memory_increment_mb` (model-load overhead) via `psutil`, useful for right-sizing deployment infrastructure.

## Monitoring with Prometheus

Access Prometheus at `http://localhost:9090`.

```promql
# Is the service healthy? (1 = up, 0 = down)
up{job="summarization_service"}

# Request rate over the last 5 minutes
rate(summarization_service_requests_total[5m])

# Average request latency over the last 30 minutes
rate(summarization_service_request_latency_seconds_sum[30m])
  / rate(summarization_service_request_latency_seconds_count[30m])

# Successful requests in the last hour
increase(summarization_service_requests_total{status="success"}[1h])
```

Toggle between the **Graph** view (time series) and **Table** view (instantaneous values) for any query.

## Dashboards with Grafana

Access Grafana at `http://localhost:3000` (`admin` / `admin`). An auto-provisioned **Text Summarization Service Performance** dashboard is included.

- **Edit a panel:** Hover → ⋮ menu → **Edit** → modify the PromQL query and visualization options → **Apply**.
- **Add a panel:** **Add Panel → Add a new panel** → select Prometheus as the data source, e.g. p99 latency:
  ```promql
  histogram_quantile(0.99, sum(rate(summarization_service_request_latency_seconds_bucket[5m])) by (le))
  ```
- **Set an alert:** In the panel editor's **Alert** tab → **Create alert rule from this panel** → define a threshold (e.g. `IS ABOVE 5` seconds) → assign a notification contact point.
- **Change time range / refresh rate:** Use the clock icon and refresh-rate dropdown in the top-right corner.

## Benchmark Results

Observed on CPU during local benchmarking (see MLflow for full, up-to-date figures):

| Model | Memory Overhead | Peak RAM | CPU Usage | Latency / Summary |
|---|---|---|---|---|
| `sshleifer/distilbart-cnn-6-6` (BART) | ~1.2–1.3 GB | ~1.7–1.8 GB | 20–24% | ~11.0 s |
| `t5-small` | ~233 MB | ~1.7–1.8 GB | ~18% | ~5.7 s |
| `google/flan-t5-small` | ~0 MB* | ~1.7–1.8 GB | — | — |

\* Measured 0 MB increment because the process already had PyTorch/transformers warmed up with a shared cache at measurement time.

**Takeaway:** `t5-small` offers roughly 2x lower latency and a much smaller memory footprint than DistilBART, at the cost of some summary quality — a favorable trade-off for low-resource deployments. Peak RAM stays similar across models because Python, PyTorch, and dataset libraries form a shared baseline footprint.

## Testing

Run the test suite, including ROUGE regression tests that guard against summary-quality regressions:

```bash

```

These tests are intended to run in CI/CD to block merges that degrade summarization quality below an accepted ROUGE threshold.
